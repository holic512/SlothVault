# 项目资料写作与工具选择

先核对源码、现有说明和截图。正文先回答项目能做什么、读者能拿到什么，再按材料需要介绍功能、截图、技术栈、源码和启动方式。不要把“角色与功能”和“功能模块”写成两份相同清单，也不要用“面向项目展示、学习参考和二次开发准备”这类句子填充篇幅。

以学生成绩管理系统为例，确认有对应功能后可以这样开头：

> 这个系统用来维护学生、课程和成绩。教师可以录入与查询成绩，管理员负责账户和课程信息。本页提供运行截图、源码压缩包和启动步骤。

如果没有查到教师账号功能，就删除那句话；只有源码、没有启动步骤时也要据实调整。接着围绕实际操作写两三段：成绩在哪里录入、查询支持什么条件、截图展示哪个页面。不要编造自动统计、权限隔离、部署成功、性能指标、售后支持或商业使用授权。

先按材料清单完成全部上传并核对成功返回值，再撰写含引用的正文。项目笔记正文图片用 `NoteImage`，ZIP/PDF 等下载附件用 `NoteAttachment`；独立文章使用 `ArticleImage` 和 `ArticleAttachment`，两套系统不得混用。上传失败停止正文写入；结果不明先回查，复用已成功上传的文件，不编造地址或写入占位链接。截图默认用 Markdown 图片内嵌到对应段落。源码和视频以下载链接说明用途。使用上传接口实际返回的 filePath 和 resourceUri，不猜测公开下载 URL；图片地址和附件链接也是正文，发布前应检查它们。授权或限制只写已确认的事实，不自动添加一大段免责声明。

- 代码统计使用宿主可用的本地工具；已安装 SlothTool 时可选用 `slothtool loc`，无需为此安装。记录统计的目录、后缀和排除范围。结果是物理行数，包含空行和注释，不能称为“有效代码量”；项目 JSON、Markdown 等非源码文件是否计入也应说明。
- 打包先查看文件清单并将输出放在源码目录外；已安装 SlothTool 时可选用 `slothtool pzip`，按当前帮助确认参数，无需额外安装。核对依赖目录、构建产物、Git 元数据及敏感配置是否排除；不能仅凭“使用了默认规则”就宣称没有敏感文件。
- 图片确需压缩时使用已安装的图片工具，先看帮助和输出位置，保留原图。已有材料和已上传文件能复用时，不重新生成或上传。

完成后用实际页面或返回内容检查图片、下载链接和段落结构。说明用了哪些真实证据；不要把工具执行过程写进项目介绍。
