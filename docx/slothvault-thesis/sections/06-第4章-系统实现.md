# 第4章 系统实现

## 4.1 开发环境与技术实现基础

系统采用 Nuxt 4 作为全栈开发框架，在同一工程内同时组织前端页面与服务端 API。前端界面基于 Vue 3 Composition API 和 Element Plus 构建，状态管理依赖 Pinia，Markdown 编辑和预览依赖 `md-editor-v3`。后端通过 Nuxt Server Routes 提供接口，并使用 Prisma 统一访问 PostgreSQL 数据库。区块链部分使用 `@solana/web3.js` 与 SPL Account Compression 相关能力处理树与压缩 NFT 业务。该技术组合一方面减少了前后端切换成本，另一方面也有利于围绕同一数据模型进行页面、接口和数据库设计。

从实现策略上看，项目并没有把“前台内容站点”和“后台管理系统”拆成两个独立仓库，而是通过不同页面布局和接口命名空间进行统一组织。这种实现方式适合毕业设计项目：既能保证代码结构集中、便于调试，也能体现同一业务模型在前台展示与后台维护两个视角下的不同用法。与传统前后端完全分离架构相比，该方案在小中型内容系统中具有更低的开发和维护成本。

## 4.2 后台管理功能实现

### 4.2.1 管理员认证实现

后台认证由初始化、登录、会话校验三部分组成。初始化页面用于创建首个管理员账号，登录接口在校验身份后创建会话记录，后台各功能接口在执行前先读取会话状态。若会话不存在或已失效，接口立即返回未授权状态，从而阻止后续业务逻辑继续执行。该设计让后台项目管理、链上资产管理和备份恢复接口能够复用同一套身份校验机制。

在实现上，认证接口和会话读取逻辑被抽离为通用工具，而不是在每个业务接口中重复处理账号判断。这样做有两个直接好处：一是减少了重复代码，二是让不同资源接口在未授权场景下拥有一致的返回行为。对于后台系统而言，这种一致性不仅提升了开发效率，也使测试章节中的未授权用例更容易建立统一预期。

### 4.2.3 分类、笔记与正文管理实现

分类和笔记管理页面通过项目、版本和分类三级筛选联动，帮助管理员快速定位到目标内容。系统将文档标题和文档正文拆为 `NoteInfo` 与 `NoteContent` 两层结构，使单篇文档既能保持稳定的逻辑条目，也能保存多个正文版本。在编辑器实现上，系统将 Markdown 编辑区与预览能力结合，便于管理员在同一工作流内完成内容录入和排版检查。Markdown 编辑与预览协同结构如图4-4所示。

正文编辑能力是平台可用性的关键组成部分。若系统只能维护标题和目录而无法高效维护正文，就无法支撑真实的文档生产场景。通过引入 Markdown 编辑器和预览组件，平台在保证内容录入效率的同时，也让正文结构、标题层级和图片链接能够在编辑阶段尽早暴露问题。对于毕业设计项目而言，这种“内容输入即预览”的实现方式比单纯文本框录入更具实际价值。

## 4.3 前台展示与访问控制实现

### 4.3.1 项目首页与文档阅读实现

前台项目首页页面在进入时先读取项目基础信息，再根据项目是否开启鉴权决定是否继续加载首页内容。若项目无需鉴权或用户已通过验证，则调用项目首页接口返回 Markdown 内容并渲染。文档阅读页则在页面加载时先读取当前版本下的分类与笔记目录，自动定位默认笔记，再获取对应正文内容并渲染目录导航。文档阅读页加载时序如图4-3所示。

该实现保证了前台体验的连续性。用户在访问文档时不需要先理解后台的数据表结构，而是通过项目首页、版本路由和笔记导航逐步进入具体正文。与此同时，前台又不会因为界面友好而绕过业务约束，因为目录数据和正文数据仍然由服务端接口控制，访问校验逻辑也仍然在请求链路中生效。

### 4.3.2 项目访问验证实现

访问验证的核心在于前后端共同执行“是否需要鉴权”和“是否具备访问资格”两个判断。前端通过组合式函数获取当前项目鉴权状态、钱包地址和验证结果，并在需要时调用 `/api/project/[id]/verify-access` 接口。服务端在接口内部首先校验项目 ID、请求体参数和钱包地址格式，然后查询项目的 `requireAuth` 状态，最后调用统一的访问校验逻辑完成判断。这样可以保证首页接口、侧边栏接口和正文接口都能复用一致的鉴权策略。

相比把权限判断分散写在各个页面或接口里，当前实现把验证逻辑收敛到统一入口，再由组合式函数和工具模块在前后端复用。这种实现方式的工程价值在于：一旦访问策略发生变化，开发者只需要调整集中逻辑，而不需要逐页排查。对于包含多个前台入口的文档平台，这种集中式鉴权方案更适合后续维护。

### 4.3.3 文档目录与预览协同实现

除了访问控制之外，前台文档阅读体验还依赖正文目录与 Markdown 预览的协同。系统在正文页面中同时维护左侧分类导航和右侧目录组件，其中左侧分类导航负责在不同笔记之间切换，右侧目录组件负责对单篇正文中的标题层级进行定位。由于正文本身来源于 Markdown 内容，这一协同关系要求前端能够在渲染后继续提取标题层级信息，而不是只做静态文本展示。

这种实现带来的好处有两个。第一，管理员在后台维护标题层级后，前台目录能够自动同步更新，不需要额外维护一套独立的目录数据。第二，终端用户在阅读较长文档时可以同时依赖“文档之间的导航”和“单文档内部的导航”，从而提高长篇内容的可阅读性。对于以技术文档为主的平台而言，这一能力比单页静态展示更符合真实使用场景。

## 4.4 区块链资产管理实现

### 4.4.1 Merkle Tree 管理实现

系统通过专门的后台页面和接口管理 Merkle Tree。树记录不仅保存链上地址，还保存最大深度、缓冲区大小、树冠深度、网络类型、容量和创建成本等参数。这些数据既影响链上成本，也直接决定后续压缩 NFT 的承载能力。后台页面需要支持树列表查看、创建准备、估算成本、提交和删除等操作。

从实现层看，Merkle Tree 管理并不是单纯展示链上返回值，而是把与业务相关的运行属性也保存在本地数据库中。这样一来，后台可以基于容量、优先级和状态决定下一次铸造应使用哪一棵树，也可以在树异常或已满时及时切换策略。这说明区块链接入层已经具备一定的本地治理能力，而不是完全把业务判断外包给远程网络。

### 4.4.2 压缩 NFT 铸造与提交流程实现

压缩 NFT 的实现包括准备会话、签名交易提交、链上确认、资产 ID 计算与数据库回写几个关键步骤。以交易提交流程为例，接口首先校验请求中的会话 ID 与交易数据是否完整，然后从本地会话缓存中读取铸造上下文；接着反序列化签名交易并校验签名数量与完整性；在发送交易后，系统等待确认结果，根据成功、失败或待定状态回写数据库。如果交易成功，系统还会基于树地址与叶子索引计算资产 ID，并写入压缩 NFT 记录。cNFT 铸造提交流程如图4-1所示。

这一路径体现出链上业务实现与普通 CRUD 接口之间的差异。普通文档接口往往只处理一次数据库读写即可完成，而 cNFT 交易提交流程涉及本地会话、用户签名、远程网络确认和本地状态回写四个阶段，任何一个阶段出现异常都可能影响最终结果。当前实现通过显式错误分类和多分支状态处理，把这一复杂过程转换成较可控的业务流程，这是系统实现层的重要难点之一。

### 4.4.5 区块链交易异常处理实现

区块链相关功能的稳定性并不只取决于成功路径，更取决于异常路径是否能够被清晰识别。当前系统在 cNFT 提交实现中区分了会话过期、签名不完整、余额不足、RPC 连接失败、交易过期和状态未知等多类情况，并分别给出不同的处理策略。例如，会话过期场景会立即中止后续流程；签名不完整场景会直接拒绝提交；而当交易状态一时无法确认时，系统会保留“铸造中”状态，避免过早把结果写死为失败。这种设计体现出实现层对链上不确定性的现实考量。

对毕业设计项目而言，这种异常处理设计比单纯展示“交易成功”更能说明系统质量。因为真实系统运行时最常见的问题往往不是理想路径是否存在，而是异常场景出现后系统是否仍然能够保持数据状态一致、是否仍然能够向操作者反馈明确原因。当前实现至少在逻辑层已经覆盖了这些问题，为后续运行级验证保留了较好的基础。

### 4.4.4 访问控制分支实现

访问控制逻辑的复杂性主要来自“公开项目”和“受保护项目”必须共存。系统通过项目字段 `requireAuth` 控制是否进入验证路径，再由访问验证接口决定最终是否允许读取正文。实现分支如表4-5所示。

表4-5 项目访问控制分支表

| 分支场景 | 条件 | 处理结果 |
| --- | --- | --- |
| 公开项目 | `requireAuth=false` | 直接返回前台内容 |
| 受保护项目但未提供钱包地址 | `requireAuth=true` 且钱包为空 | 拒绝访问并提示连接钱包 |
| 本地记录命中 | 钱包地址与本地 cNFT 记录匹配 | 允许访问 |
| 本地记录未命中但链上验证成功 | 链上资产持有状态匹配 | 更新本地记录后允许访问 |
| 链上验证失败 | 无匹配资产或 RPC 异常 | 拒绝访问并返回原因 |

这种实现分支让系统在访问控制上既不失灵活性，也不过度依赖链上实时查询。对于公开项目，平台仍然可以保持普通文档站点的访问体验；对于受保护项目，平台则引入更严格的资产验证逻辑。

## 4.5 备份恢复实现

系统将数据备份拆分为数据库业务数据备份和文件备份两类。数据库导出接口会统一汇总项目、版本、分类、笔记、正文、文件、系统配置、系统首页、Merkle Tree 与压缩 NFT 数据，并对 `BigInt` 类型进行字符串化处理，便于后续导入恢复。该设计一方面避免直接暴露认证数据，另一方面也让业务备份结构更清晰。文件备份则围绕上传目录进行处理，保证内容数据与附件资源可以一起恢复。

这一实现说明项目在工程闭环上已经超出了“功能演示系统”的范围。许多课程项目只关注页面展示和基础增删改查，而忽略系统迁移和数据恢复。SlothVault 在代码层面显式提供备份接口，意味着开发者已经把系统的持续维护与异常恢复纳入设计考虑，这对于毕业设计的完整性是加分项。

### 4.5.1 数据导出对象组织

数据库导出逻辑并不是简单执行一张表的全量查询，而是同时读取项目、项目版本、分类、笔记、正文版本、文件、系统配置、系统首页、Merkle Tree 与压缩 NFT 等多类业务对象，再通过字符串化处理解决 `BigInt` 字段在 JSON 输出中的兼容问题。这种组织方式使导出的备份文件更接近一个业务快照，而不是零散数据片段。

| `compressedNfts` | 资产记录 | 恢复访问凭证映射 |

### 4.5.2 导入恢复的工程意义

恢复能力的意义不仅在于灾难恢复，还在于开发环境迁移、测试数据复用和系统部署迭代。对于一个包含链上凭证映射的文档平台而言，如果只能恢复正文内容而无法恢复项目与资产关系，那么前台访问控制链路就会被破坏。因此，备份恢复模块虽不是用户最常见的交互界面，却是系统实现层不可忽略的关键能力。

### 4.5.3 数据一致性保障实现

备份恢复模块还承担着保持数据一致性的职责。由于项目、版本、分类、笔记、正文和资产映射之间存在层层依赖关系，任何单一对象的缺失都可能导致前台展示链条中断。例如，如果恢复了 `NoteContent` 而没有恢复对应的 `NoteInfo`，前台就无法正确构造侧边栏与正文的关系；如果恢复了项目和正文却缺少 `CompressedNft` 记录，受保护项目的访问验证又会失去依据。因此，系统在实现备份逻辑时需要把多类对象视为一个业务整体，而不是孤立的数据片段。

从实现意义上讲，这种一致性考虑使系统更接近真实运维场景。它表明开发者已经意识到“系统功能完成”并不等于“系统可长期维护”，后者还要求在部署迁移、环境重建和数据恢复过程中保持业务结构不被破坏。这一点也是本项目在实现层较为完整的体现。

## 4.6 本章小结

本章围绕后台管理、前台展示、访问鉴权、区块链资产处理和备份恢复五个方面说明了系统实现方式。实现结果表明，SlothVault 并非简单地把区块链接入到一个已有内容平台，而是在项目访问控制、资产状态回写和文档展示流程中形成了相互联动的实现体系，这为后续测试与分析提供了具体对象。
