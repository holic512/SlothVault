# 第1章 绪论

## 1.1 课题背景

随着软件产品形态从单机文档逐步转向在线知识库、课程内容平台和项目化文档站点，文档系统已经不再只是静态文件仓库，而是逐渐演变成兼具内容生产、版本组织、访问控制和资源分发能力的综合平台。对于技术团队、课程组织者和内容服务提供者而言，文档平台不仅需要支持文本编辑和多级目录管理，还需要解决以下几个现实问题：其一，文档内容会随着项目版本持续演化，系统必须支持稳定的版本管理与目录组织；其二，文档内容通常具有一定访问门槛，需要对不同用户实施差异化授权；其三，随着数字资产技术的发展，平台希望把访问凭证设计为可校验、可流转且成本可控的数字权益载体。

传统文档管理系统多以账号、角色、数据库记录为核心完成权限控制，这种模式在企业内部使用场景中具备成熟优势，但在面向链上用户、数字权益分发和跨平台访问验证场景时存在一定局限。一方面，平台自身保存权限状态，外部难以独立验证；另一方面，访问凭证缺乏统一的资产化表示，不利于在不同系统之间形成可信迁移。区块链技术的发展为这类问题提供了新的工程路径。通过链上不可篡改记录、哈希摘要和可验证资产，系统能够在不暴露文档内容本身的前提下，对访问资格进行独立核验[1-4]。

从工程实现角度看，文档平台与区块链技术的结合并不意味着把所有内容直接迁移到链上。实际业务中，文档正文往往更新频繁、体量较大、结构复杂，若强行全部上链，不仅会推高成本，也会让内容维护过程变得僵化。因此，更合理的思路是在链下维护文档主体，在链上维护能够表达访问资格或资产归属的凭证信息，再由服务端完成两者之间的映射。这样既能够保留传统文档系统在编辑、版本管理和运维上的优势，也能够借助区块链资产增强访问控制的可信度。

在众多区块链平台中，Solana 以高吞吐、低成本和成熟开发工具链受到关注。进一步地，压缩 NFT 技术通过状态压缩和并发 Merkle Tree 降低了大规模 NFT 铸造的链上成本，使“以资产作为访问凭证”的设计更适合工程落地[5][6]。因此，将压缩 NFT 与传统文档平台结合，可以形成一种“链下存内容、链上存凭证、服务端做协同验证”的混合架构。SlothVault 项目正是在这一思路下构建：系统在后台完成项目、版本、分类、笔记和文件的常规管理，在前台提供项目首页和文档阅读能力，同时为需要保护的项目启用基于 cNFT 的访问校验。

本课题选取 SlothVault 作为研究对象，还有一个直接原因，即该项目并不是纸面上的概念原型，而是已经具备前后端页面、数据库模型和区块链接口实现的完整工程仓库。通过分析这类真实项目，可以把毕业论文的研究对象从抽象的“基于区块链的文档平台设想”收敛为“具备明确模块边界和数据实体的实现系统”，从而使需求分析、系统设计、实现说明和测试方案都拥有可回溯的代码证据支撑。

## 1.2 研究目的与意义

本课题的直接目标是设计并实现一套可运行的文档管理系统，使其既具备传统内容平台需要的管理能力，又能够通过区块链资产完成项目级阅读权限控制。围绕这一目标，系统需要在三个层面完成平衡：第一，内容管理层必须保证结构清晰、编辑高效和版本可维护；第二，权限控制层要让项目是否需要鉴权、用户是否具备访问资格、验证失败后如何提示等流程具有明确边界；第三，区块链接入层应尽量减少链上成本和对普通文档功能的侵入。

对于软件工程专业毕业设计而言，这种平衡具有较强的综合训练价值。内容管理部分要求开发者完成典型的信息系统建模与前后端协同；权限控制部分要求开发者处理角色边界、状态判断和异常分支；区块链接入部分则要求开发者理解外部系统调用、异步交易确认和本地数据回写逻辑。三者叠加后，课题能够较完整地体现需求分析、数据建模、模块设计、接口开发和系统测试等软件工程核心能力。

从工程实践角度看，本课题具有以下意义。首先，它验证了压缩 NFT 不仅可以服务于数字藏品等资产场景，也可以作为文档访问凭证接入内容系统，为知识付费、技术文档服务和内容会员体系提供新的实现方式。其次，课题将 Nuxt 全栈开发、Prisma 多 schema 建模、Markdown 编辑预览与 Solana 资产验证整合到同一项目中，对前后端协同设计和数据库边界划分具有较强的软件工程训练价值。最后，通过把 Merkle Tree、交易确认、资产状态回写等链上逻辑与本地项目元数据关联，系统为“内容系统 + 区块链鉴权”的组合提供了较完整的模块化实现样本。

从应用意义看，这一方案适用于多种需要内容门槛控制的场景。例如，面向企业知识库的内部文档可通过资产化凭证进行组织级分发；面向技术课程的学习资料可通过链上凭证控制阅读范围；面向付费报告或行业白皮书的平台也可以借助类似机制实现更加可核验的会员访问模式。虽然本课题并不直接验证所有商业模式，但它至少说明了“基于区块链资产的访问控制”在文档系统中具有可实现性，而不仅停留在概念讨论层面。

## 1.3 国内外研究现状

现有文档管理系统研究主要集中在内容组织、协同编辑、权限控制和分布式存储等方向。国外主流开源文档平台强调全栈渲染、静态生成或知识库协作能力，而数据库与 ORM 工具的发展则使文档系统在模型维护和接口演进方面更容易形成规范化工程实践[7-10]。对于需要复杂访问控制的数字内容系统，研究者开始尝试将区块链引入权限校验、可信共享和安全存储等场景，通过哈希结构、智能合约和加密机制增强凭证可信度[3][4][11]。

从内容平台的发展轨迹看，文档系统已经逐步摆脱了“文件上传下载器”的单一定位，开始承担知识组织、内容迭代、版本发布和资源运营等职责。这一变化使文档平台在系统设计上越来越接近内容管理系统与知识库系统的综合体，也意味着权限控制机制不能再停留在简单的页面可见性开关层面，而需要能够跟随项目、版本和用户身份动态变化。

围绕区块链访问控制与安全存储的研究，已有工作指出中心化权限视图在跨域数据流通场景中容易带来可信边界单一和状态维护复杂的问题，因此引入区块链账本、Merkle Tree 或零信任式身份校验有助于提升访问控制可验证性[2][12][13]。同时，IPFS 与区块链结合的安全存储方案表明，链上链下混合架构更适合处理容量较大的业务数据，即把完整内容保留在外部存储或业务数据库中，把可信摘要、标识或访问凭证放到链上[14]。这一思路与文档平台的业务特点高度一致，因为文档正文更新频繁且体量较大，直接全量上链既没有必要，也会显著推高成本。

不过，从已有研究到实际工程落地之间仍存在明显差距。许多工作更加关注理论协议、安全模型或单一技术点，而对于内容平台中常见的项目管理、版本迭代、正文编辑和后台维护等工程细节涉及较少。换言之，区块链访问控制机制本身可以被证明有效，但若缺少与真实业务数据结构、前端交互流程和后台维护能力的结合，就难以形成真正可用的系统。因此，本课题的价值之一就在于把这些抽象机制嵌入到可运行的文档平台中加以验证。

在 Solana 生态中，压缩 NFT 利用状态压缩和 Bubblegum 程序降低大规模资产铸造成本，使 NFT 从单纯收藏型数字资产拓展到可验证凭证领域[5][6]。官方文档表明，压缩 NFT 的核心不在于把完整元数据直接保存在链上，而在于把能够验证资产状态的哈希信息写入并发 Merkle Tree，再结合链下索引与证明机制完成读取和校验[5]。这为文档访问控制提供了现实基础：系统不需要把文档内容上链，只需把项目关联的访问凭证资产与本地项目记录绑定，即可在阅读请求到来时根据钱包地址校验用户是否具备访问资格。

这一点对本课题尤为关键。因为毕业设计系统的重点并不在于构造一个完整的链上内容分发协议，而在于利用现有区块链能力改造传统文档平台的访问控制方式。压缩 NFT 正好满足了这一需求：它既具备链上可验证性，又避免了普通 NFT 在批量发行场景下的高成本问题，因此能够成为项目级访问凭证的合适实现载体。

总体来看，国内外相关研究已经为本课题提供了三个启发。第一，文档平台本身应坚持内容管理与结构组织的工程主线，而不是为了区块链而牺牲可维护性。第二，区块链更适合作为访问凭证和可信校验基础设施，而非直接替代全文内容存储。第三，低成本、可批量发行的链上资产机制是内容系统接入区块链的关键前提。基于这些认识，本文选择在传统文档管理系统之上叠加压缩 NFT 访问控制，形成一套更符合实际工程边界的实现方案。

### 1.3.1 现有研究存在的不足

尽管相关研究已经提出了不少有价值的技术路线，但仍存在三个方面的不足。其一，许多研究偏重理论模型，缺乏与真实内容平台相匹配的数据结构设计和页面交互设计。其二，部分方案强调链上可信，却忽视了系统维护成本和编辑效率，导致工程落地难度偏高。其三，部分工作虽然提到了链上链下协同，但没有进一步说明资产状态如何与业务对象形成稳定映射。上述不足正是本文在系统设计和实现过程中需要重点回应的问题。

### 1.3.2 本文研究与相关工作的区别

与只讨论区块链安全模型或只实现普通知识库平台的研究相比，本文的区别主要体现在三个方面。第一，本文以真实工程仓库作为分析对象，而不是从空白需求出发构造抽象系统，这使论文中的章节能够更紧密地围绕实际代码证据展开。第二，本文关注的是“文档内容管理系统如何接入压缩 NFT 访问凭证”这一工程问题，而不是单纯讨论 NFT 技术本身，因此重点放在项目、版本、正文、访问控制和资产映射的协同上。第三，本文在分析过程中始终保留“保守取证”的边界，避免将 README 中的宣传性描述直接写成系统已完成能力，这一点有助于提高论文论证的可信度。

从成果形态看，本文最终交付的不是一套分散的技术片段，而是一条完整的软件工程链路：需求分析对应系统角色和业务目标，系统设计对应模块与数据库模型，系统实现对应页面、接口和工具函数，系统测试则对应功能闭环和异常路径。这种结构比单纯罗列技术栈更能够体现毕业设计论文的研究深度和工程价值。

## 1.4 研究内容

围绕论文题目，本文的研究内容主要包括以下几个方面：

1. 分析面向项目化文档服务的业务需求，明确管理员、普通访客和持证访问用户的角色边界，归纳文档管理、版本组织、内容发布、访问验证和备份恢复等核心需求。
2. 设计系统总体架构，建立前台展示、后台管理、数据库持久化、区块链资产管理和文件存储之间的协同关系。
3. 结合 Prisma 多 schema 数据模型，完成用户、会话、项目、项目版本、分类、笔记、笔记内容、文件、Merkle Tree 和压缩 NFT 等实体设计。
4. 基于 Nuxt 4 和 Vue 3 实现后台管理页面与前台阅读页面，基于服务端 API 实现项目管理、文档管理、访问验证和 cNFT 铸造处理逻辑。
5. 设计系统测试方案，对登录鉴权、项目管理、文档阅读、区块链资产管理和备份恢复等模块建立测试用例与验证路径。

在研究方法上，本文主要采用仓库代码取证、系统结构分析、数据模型抽取、业务流程归纳和测试方案设计相结合的方式展开。对于源码能够直接证明的功能，正文按“已实现”表述；对于需要在运行环境中继续验证的内容，则保守地写成“测试方案”或“待补证据”，从而保证全文叙述与项目现状保持一致。

## 1.5 论文结构安排

本文共分为五个主体章节。第1章阐述课题背景、研究意义、国内外研究现状、研究内容与论文结构安排。第2章从业务目标和用户角色出发，对系统功能需求、非功能需求和关键业务流程进行分析。第3章对系统总体架构、模块设计、接口协作和数据库设计进行详细说明。第4章结合关键页面、接口流程和工具模块，对系统实现进行展开。第5章给出测试环境、测试方法、测试用例与结果分析。最后在结论部分总结本文工作，并说明当前系统仍然存在的不足和后续改进方向。

这种章节安排遵循了“先需求、后设计、再实现、最后测试”的软件工程论文基本逻辑，同时也适配了本项目的真实证据形态。由于仓库中已经存在较完整的数据模型、接口与页面实现，因此论文主体的重点不再是抽象技术介绍，而是围绕系统如何从需求走向落地进行结构化说明。
