# 本地完整备份与恢复

SlothVault 提供完整 ZIP 备份和本地每日自动备份。手动备份、自动备份及恢复前保护备份共用同一套生成和校验流程。部署按单个 Node.js 进程或容器运行；进程内维护锁及任务互斥不适用于多个应用副本共享业务库或上传目录。

## 开启与存储

在后台 **备份管理 → 自动备份设置** 手动开启。默认每日 `Asia/Shanghai` 时间 **03:00** 执行，保留最近 **7 份成功的自动备份**。可以调整每日时间、IANA 时区及 1–365 份保留数量。

- 默认目录：`${APP_DATA_PATH}/backups`。
- 自定义独立本地磁盘：部署时设置 `BACKUP_STORAGE_PATH`，重启应用后后台显示实际位置及可用空间。
- 目录使用 `0700`，备份和控制记录使用 `0600`。应用进程必须有写入权限。
- 备份目录必须与上传、配置和数据库目录隔离，不能相同、互为父子目录，或通过符号链接指向这些位置。
- 调度策略、任务记录、上传暂存索引、预检和恢复日志保存在 `${APP_DATA_PATH}/config/backup-state`。它们不进入业务备份、不随业务恢复替换。请持续挂载配置目录。

容器使用独立本地磁盘时，在所用 Compose 文件的应用服务中增加自己的挂载，例如：

```yaml
services:
  slothvault:
    environment:
      BACKUP_STORAGE_PATH: /app/backups
    volumes:
      - /mnt/backup-disk/slothvault:/app/backups
```

保留当前 Compose 模板原有的数据和上传挂载，将上述字段合并到实际应用服务，使用实际服务名。容器用户需要拥有该目录的写权限。修改存储路径不会移动旧备份或其索引；切换路径应在应用停止时把原目录内容完整复制到新盘并保留权限，再修改变量启动。对使用远程 SQL 服务的部署，这仍是应用所在主机的本地磁盘。

## 自动执行与任务状态

首次开启时安排下一次计划，不立即补执行开启前的历史任务。已经开启的系统重启后，只补执行最近一次遗漏的日期；不会积压所有漏掉的日期。夏令时跳过执行时间时，在该日第一个晚于设定时间的本地分钟触发；重复的本地时间在同一天只执行一次。

启动入口只注册一个调度器，生产构建不启动备份。未安装、维护中或已有备份/恢复任务时不执行。任务状态和阶段持久化，包括排队、运行、成功、失败、中断、耗时与脱敏错误。浏览器关闭不会取消服务端任务；重新进入后台查看历史即可。失败或中断的备份可以重新执行，重试会读取当时的最新业务状态。

仅在新自动备份完成全部校验并发布成功后，才清理超出保留份数的旧自动备份。手动备份、恢复前保护备份、正在下载或用于预检/恢复的备份不参与自动清理。清理失败是独立警告，新备份仍为成功。中断产生的临时 ZIP 不显示为可恢复备份。

## 备份范围与格式

完整 ZIP 恰好包含：

| 条目 | 内容 |
| --- | --- |
| `database.json` | `2.10.0` 业务数据，包括用户资料/凭据/积分、卡密、会员权限、文章、项目、回收站、停用文件记录、文件关联、配置、合同、委托及发布/交易存证。 |
| `files.zip` | 上传目录中的可见常规文件及目录，不包含隐藏的运行暂存和回滚材料。符号链接和特殊文件会导致备份失败。 |
| `manifest.json` | 格式版本 1、备份 ID、生成时间、应用版本、数据库格式、各集合数量、文件路径/大小/SHA-256，以及数据库 JSON 和附件 ZIP 的 SHA-256。 |

在维护锁内读取数据库事务快照并复制附件，复制完成后释放锁，再压缩及校验。网站写入、MCP 鉴权与工具执行、后台备份和恢复通过同一锁协调。托管附件缺失、大小不符、委托或合同附件冻结哈希不符均导致明确失败。

新格式要求全部有效业务集合显式出现；空集合使用空数组。独立数据库导入和完整包中的数据库数据继续接受 `2.0.0`–`2.9.0`，旧格式缺失的集合按兼容规则处理，预检会警告覆盖范围差异。`2.0.0`–`2.8.0` 的历史合同及已移除的 Tree/cNFT 数据不恢复；`2.9.0` 的委托合同继续恢复。数据库和文件仍可独立导入/导出，但两次独立操作不提供完整包的一致性保障。

| 限制 | 上限 |
| --- | --- |
| 数据库 JSON | 50 MiB / 合计 100,000 条记录 |
| 附件 ZIP | 250 MiB |
| 单个解压条目 | 256 MiB |
| 附件解压合计 | 1 GiB |
| ZIP 条目 | 10,000 |
| 路径 | 1,024 字节 |
| 完整 ZIP | 320 MiB |

生成端和恢复端使用相同限制。恢复先验证 ZIP 路径、重复/特殊条目、压缩方法、条目大小、CRC、SHA-256、数据库关系和冻结存证。解压和保护备份需要额外磁盘空间；空间不足时停止，不会清理旧备份来腾挪空间。

## 完整恢复

1. 选择历史备份的“恢复预检”，或上传完整 ZIP。上传走有界流式接口，暂存有效期为 1 小时。
2. 查看时间、数量、版本、覆盖范围、兼容警告及当前管理员例外。预检绑定当前管理员和源文件哈希，有效期 10 分钟。
3. 输入 `RESTORE_BACKUP`，确认完整覆盖。只提供覆盖模式。
4. 服务端重新检查源文件与账号冲突，在独占维护锁内先生成恢复前保护备份。保护失败则停止。
5. 附件通过暂存和回滚目录切换；数据库在同一个事务内导入业务数据并写入提交标记。数据库失败则回滚附件。数据库成功提交后的缓存刷新或材料清理失败仅记录警告。
6. 等待任务成功，再检查关键业务数据和附件。保护备份可在历史或任务记录中下载。

账号恢复保留当前操作管理员的用户名、密码/钱包/邮箱登录凭据、管理员身份及当前会话。备份包含对应账号时恢复其业务资料和积分；缺少该账号时保留账号并将积分余额重置为 0。其他账号恢复备份状态，备份中不存在的账号移除，其旧会话和 MCP Key 撤销。与保留管理员凭据发生唯一性冲突时预检拒绝；MySQL 还会按实际字段排序规则检查备份内部的用户名、邮箱和钱包重复。独立数据库“插入模式”遇到现有用户名、凭据或配置键冲突，会拒绝整个事务。

业务恢复不替换目标环境的数据库连接、安装绑定、主密钥和备份控制状态。迁移到另一台主机或另一种数据库时，先独立安装目标环境、创建用于恢复的管理员，再上传完整包。主密钥及安装配置仍由部署管理，并单独备份。

## 中断与维护状态

切换附件前，应用将恢复意图和原/新根目录名称写入持久化日志，并同步文件和目录。数据库事务内写入专用提交标记；该标记不进入导出数据。

重启时，应用先检查恢复日志：存在提交标记则保留新数据并完成清理，否则撤销未提交的文件切换。恢复决定在删除材料前持久化，清理可重复执行。提交状态、日志或文件状态无法确认时，系统进入维护状态，保留日志、暂存和回滚目录，停止业务写入。不要删除 `config/backup-state/restore.json` 或上传目录下的 `.complete-restore-*`、`.complete-rollback-*` 来绕过维护；先恢复原数据库可达性和磁盘权限，再重启让应用协调。

备份目录本身不可用会在后台显示存储错误，不会自动改用业务目录。维护及任务错误使用脱敏代码；排查文件系统权限、磁盘剩余空间和数据库连接时不要把连接串、Cookie、Token 或密码放入日志。

## HTTP 接口

全部接口使用管理员 Session，位于 `/api/admin/mm/backup`。控制请求的 JSON 限制为 4 KiB；ZIP 上传使用原始 `application/zip` 请求体。

| 方法与路径 | 请求或结果 |
| --- | --- |
| `GET/PUT settings` | 读取状态；保存 `enabled`、`dailyTime`、`timeZone`、`retentionCount`。 |
| `GET snapshots` | 完整备份摘要、最近 100 个任务和当前任务。 |
| `POST snapshots` | 创建手动备份；可传失败/中断任务的 `retryJobId`。返回 202 和任务。 |
| `GET snapshots/[id]/download` | 使用服务端备份 UUID 下载 ZIP。 |
| `DELETE snapshots/[id]` | 传 `{ "confirm": "DELETE_BACKUP" }`，拒绝删除使用中的包。 |
| `POST imports` | 上传 ZIP，返回管理员绑定的 `importId`。 |
| `POST restores/preview` | 传 `{ "snapshotId": "UUID" }` 或 `{ "importId": "UUID" }`，返回预检。 |
| `POST restores` | 传 `{ "previewId": "UUID", "confirm": "RESTORE_BACKUP" }`，返回 202 和恢复任务。 |
| `GET jobs/[id]` | 查询任务状态与阶段，不持有全局维护锁。 |

本地备份仍应另行复制到另一块磁盘或外部介质；与业务数据放在同一块盘的备份不能覆盖磁盘损坏。完整包包含密码哈希和个人数据，按敏感文件管理。SHA-256 用于完整性检测，不构成备份来源的数字签名；只恢复可信来源的包。

## 开发验证

默认的完整备份测试使用临时 SQLite 数据库和上传目录：

```bash
npm test -- src/server/services/admin-backup/complete.integration.test.ts
```

同一套测试也支持 `SLOTHVAULT_BACKUP_TEST_PROVIDER=mysql` 或 `postgresql`，并通过 `SLOTHVAULT_BACKUP_TEST_CONTAINER` 指定专门创建的 Docker 容器完整 ID。测试只接受带 `slothvault.test=backup` 标签、数据库端口绑定到 `127.0.0.1` 的容器，在容器中逐项创建和删除独立测试库，不读取安装中的数据库配置。不要将这些变量指向业务容器。MySQL 容器使用测试专用的无密码 root；PostgreSQL 容器使用测试专用的 trust 认证。

当前 MySQL 历史迁移 `20260820000000_note_content_evidence` 会删除仍被外键使用的 `uq_release_credential_version_network` 索引，原样初始化隔离库会报 `ERROR 1553`。备份测试仅在临时库中提前补充等价普通索引，以验证备份服务；这不表示原有 MySQL 安装迁移已通过，也不修改已部署的迁移历史。
