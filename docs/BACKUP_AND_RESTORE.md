# 本地完整备份与恢复

SlothVault 提供完整 ZIP 备份、本地每日自动备份和备份文件导入。手动备份、自动备份及恢复前保护备份共用同一套生成和校验流程；导入备份复用完整包校验，并将原始 ZIP 保存为持久备份节点。部署按单个 Node.js 进程或容器运行；进程内维护锁及任务互斥不适用于多个应用副本共享业务库或上传目录。

## 开启与存储

在后台 **备份管理 → 自动备份设置** 手动开启。默认每日 `Asia/Shanghai` 时间 **03:00** 执行，保留最近 **7 份成功的自动备份**。可以调整每日时间、IANA 时区及 1–365 份保留数量。

- 默认目录：`${APP_DATA_PATH}/backups`。
- 自定义独立本地磁盘：部署时设置 `BACKUP_STORAGE_PATH`，重启应用后后台显示实际位置及可用空间。
- 目录使用 `0700`，备份和控制记录使用 `0600`。应用进程必须有写入权限。
- 备份目录必须与上传、配置和数据库目录隔离，不能相同、互为父子目录，或通过符号链接指向这些位置。
- 调度策略、任务记录、上传暂存索引、预检和恢复日志保存在 `${APP_DATA_PATH}/config/backup-state`。它们不进入业务备份、不随业务恢复替换。请持续挂载配置目录。

容器使用独立本地磁盘时，在所用 Compose 文件的应用服务中增加自己的挂载，例如：

```yaml
services:
  slothvault:
    environment:
      BACKUP_STORAGE_PATH: /app/backups
    volumes:
      - /mnt/backup-disk/slothvault:/app/backups
```

保留当前 Compose 模板原有的数据和上传挂载，将上述字段合并到实际应用服务，使用实际服务名。容器用户需要拥有该目录的写权限。修改存储路径不会移动旧备份或其索引；切换路径应在应用停止时把原目录内容完整复制到新盘并保留权限，再修改变量启动。对使用远程 SQL 服务的部署，这仍是应用所在主机的本地磁盘。

## 自动执行与任务状态

首次开启时安排下一次计划，不立即补执行开启前的历史任务。已经开启的系统重启后，只补执行最近一次遗漏的日期；不会积压所有漏掉的日期。夏令时跳过执行时间时，在该日第一个晚于设定时间的本地分钟触发；重复的本地时间在同一天只执行一次。

启动入口只注册一个调度器，生产构建不启动备份。未安装、维护中或已有备份/恢复任务时不执行。任务状态和阶段持久化，包括排队、运行、成功、失败、中断、耗时与脱敏错误。浏览器关闭不会取消服务端任务；重新进入后台查看历史即可。失败或中断的备份可以重新执行，重试会读取当时的最新业务状态。

仅在新自动备份完成全部校验并发布成功后，才清理超出保留份数的旧自动备份。手动备份、导入备份、恢复前保护备份、正在下载或用于预检/恢复的备份不参与自动清理。清理失败是独立警告，新备份仍为成功。中断产生的临时 ZIP 不显示为可恢复备份。

## 备份范围与格式

完整备份采用平铺 **ZIP64**，`formatVersion: 2`，当前业务数据版本为 `2.21.0`：

| 条目 | 内容 |
| --- | --- |
| `manifest.json` | 备份 ID、时间、应用/业务版本、各集合数量、数据库和文件索引的大小与 SHA-256，以及附件数量和总字节数。 |
| `database/<collection>.ndjson` | 每个当前业务集合一个文件，每行一条记录；空集合也必须显式存在。包含用户资料/凭据/积分、账号删除日志与历史操作者归因、卡密、会员权限、文章、项目、回收站、停用文件、文件关联、配置、历史合同、委托及发布/交易存证。 |
| `files.ndjson` | 可见文件与目录索引，记录相对路径、类型、大小和文件 SHA-256。 |
| `uploads/...` | 上传目录的可见常规文件与目录，直接放入完整包。隐藏运行材料不进入包；符号链接和特殊文件会导致失败。 |

在维护锁内按主键分页读取数据库事务快照（每批最多 100 条），并复制附件；快照完成后释放锁，再以压缩等级 1 生成 ZIP64 和流式校验。验证不再次解压全部附件。数据库记录、关联检查与恢复 ID 映射使用私有临时 SQLite 索引；任务及历史接口只返回摘要。ZIP 库的中央目录元数据仍随条目数增加而占用内存。

取消完整包总大小、单附件大小、附件总量、条目数、数据库总大小及记录数量的人为上限。实际容量取决于磁盘空间、运行时间和系统资源。路径仍限制为 1,024 字节，业务字段和整数范围仍验证；上传每次请求最多 8 MiB，NDJSON 单行按 8 MiB 校验以保持有界解析。这些约束不限制整个备份的大小。

当前接受完整包格式 2 和业务数据版本 `2.21.0`，并显式支持将 `2.13.0` 至 `2.20.0` 转换为当前数据契约。独立数据库 JSON、独立附件 ZIP、旧完整 ZIP 和未注册兼容规则的数据版本均返回 `BACKUP_UNSUPPORTED_FORMAT`。历史合同和委托记录仍进入当前包。升级保留已有旧包，不自动迁移或删除，后台显示源数据版本、当前数据版本及不可恢复原因；不兼容的自动备份也不参与自动保留策略的清理。独立数据库/文件导入导出入口和四个接口已移除。

应用发布版本、备份业务数据版本和数据库结构修订是独立概念。应用版本不同但备份数据格式相同，仍可导入和恢复。数据库增加索引等不改变可移植备份数据契约的变更，不单独使备份失效。数据契约改变时，应在 `compatibility.ts` 中显式注册源版本校验与转换适配器，并补充测试。当前注册 `2.13.0` 至 `2.21.0`；旧版本先按原结构校验，再补充历史操作者归因、单钱包绑定、文档基线及菜单图标，不允许旧格式携带新版字段或空的原必填操作者引用。转换只能作用于临时记录索引，必须先校验原始字节及源数据，再验证转换后的当前结构，不改写原始 ZIP。恢复覆盖的是当前数据库结构中的业务数据，不回退程序版本或数据库表结构。

`2.19.0` 保存项目菜单原始 `icon` 稳定键：`null` 表示自动选择，`none` 表示隐藏。父子菜单及回收站菜单均保留该值；`2.13.0` 至 `2.18.0` 的菜单转换后补 `null`。仅 `2.13.0` 至 `2.17.0` 转换时清理已退役卡密数据，`2.18.0` 及当前格式保留正常插件数据。

`2.21.0` 原样保存项目、版本、文档笔记与独立文章的 `publicId` 和 `legacyUrlId`。即使恢复后内部自增 ID 改变，公开链接及历史正文中的数字链接映射仍保持稳定；正文、发布 manifest 与存证哈希不改写。旧版本先按源契约校验，再在临时索引中分配随机公开标识并保存源编号；当前格式缺失、重复或格式错误的公开标识会被拒绝。旧格式本身不含公开标识，重复独立恢复旧包会重新生成公开标识；首次恢复后应创建新版完整备份。

结构修订 `23` 将上述四类资源的公开地址改为固定的小写 UUID v4；旧数字公开入口返回 404。历史 Markdown/HTML 中的站内链接仅在展示副本中转换，代码示例与原始发布字节保留。项目至少存在一个有效发布版本才公开。MCP 大纲的 `url` 始终使用公开标识，草稿另有管理员专用 `previewUrl`；正文引用使用 `url`，整数预览地址只用于当前安装的管理导航。公开标识降低枚举风险，正文、附件和存证仍独立执行权限校验。

恢复保留当前执行管理员的登录配置，并继续导入来源备份中的管理员账号。站点业务归整个站点管理，不挂载到某一个管理员；恢复后可通过用户管理删除多余账号。删除记录按稳定 UUID 去重合入，本站已有历史不会被覆盖；历史删除记录不阻止较旧备份重新创建当时存在的账号。操作者快照保留来源身份，恢复 ID 映射只调整可用账号引用，不重写合同、委托或链上存证的冻结内容。

生成和预检验证安全路径、重复/特殊条目、压缩方法、实际长度、CRC、SHA-256、唯一性、关联、发布内容快照与委托事件链。托管附件缺失、大小不符或冻结哈希不符均明确失败。磁盘检查按当前阶段新增空间估算，保留 256 MiB 余量；实际写入时的空间、权限或 I/O 错误仍会停止操作。不会删除旧包来腾空间。

数据库备份与恢复事务默认超时 **1 小时**，可设置 `BACKUP_DATABASE_TRANSACTION_TIMEOUT_MS`（正整数毫秒，最大 2,147,483,647；无效值回退默认值）。压缩、传输和预检不占用数据库快照/恢复事务时间。跨数据库恢复仍使用相同的可移植数据转换。

## 上传与下载续传

浏览器顺序上传 8 MiB 分片，每个分片带偏移量和 SHA-256。服务端先写临时分片并验证，再写入主文件、同步磁盘并持久化已确认偏移量。相同分片重试保持幂等；响应丢失时先查询服务端偏移量，避免重复追加。失败自动重试三次后暂停。

通过反向代理部署时，代理的单次请求体限制也必须允许至少 8 MiB 的二进制分片；备份总大小无需作为代理请求体上限。如果分片请求在到达应用前返回 413，应检查实际代理的请求体限制。

可以暂停、继续或取消。刷新后重新选择原文件，通过大小、修改时间和首尾各 64 KiB 内容指纹匹配会话，再从服务端已确认位置继续。会话在 **24 小时无上传活动**后过期；正在预检、恢复或有效预检引用的源文件不会清理。服务重启保留已确认分片，修整未确认尾部，清理中断分片。只有全部字节确认后才能将上传原子完成为不可变导入源。

在后台选择“导入备份”后，上传完成立即启动服务端校验任务，检查 ZIP、路径、CRC、SHA-256、数据格式、关联、附件和存证。校验通过后将原始包发布到正式备份存储，不重新压缩，不自动打开恢复预检，也不修改现有业务数据。备份历史显示“导入备份”、原始备份时间、导入时间和文件名，可下载、手动恢复或删除。已发布节点长期保留，不受上传会话过期影响。

同一上传会话重复提交导入请求会返回已有任务或结果；重新上传同一文件可以创建另一节点。本地节点 ID 使用服务端上传会话 UUID，包内原始 ID 保留在清单中。发布前将校验结果及发布意图同步到控制记录，重启时先校验并协调移动后的文件和索引，再判断任务结果。尚未完成校验的任务标记为中断，可以继续校验已上传文件，无需再次传输；失败材料仍可取消或在会话过期后清理。导入阶段不检查与当前管理员的凭据冲突，这类环境相关检查在恢复时执行。

下载使用浏览器原生下载，提供 `HEAD`、`Accept-Ranges: bytes`、基于整个文件 SHA-256 的强 ETag、单区间 `Range` 和 `If-Range`。有效范围返回 206，超出范围返回 416，不匹配的 `If-Range` 返回完整 200；多区间请求按完整下载处理。连接期间固定源文件，结束、取消或错误时释放引用。浏览器或下载工具是否自动续传取决于客户端。

## 完整恢复

1. 选择历史备份的“恢复预检”。外部完整 ZIP 先通过“导入备份”校验并加入历史，再手动选择恢复。预检以后台任务运行，接口立即返回 202，可查询记录/文件/字节进度；此前的导入校验不能替代本次预检和执行前复检。
2. 查看时间、数量、版本、覆盖范围、校验提示及当前管理员例外。预检绑定当前管理员和源文件哈希，有效期 10 分钟。
3. 输入 `RESTORE_BACKUP`，确认完整覆盖。只提供覆盖模式。
4. 服务端重新检查源文件与账号冲突，在独占维护锁内先生成恢复前保护备份。保护失败则停止。
5. 附件通过暂存和回滚目录切换；数据库在同一个事务内导入业务数据并写入提交标记。数据库失败则回滚附件。数据库成功提交后的缓存刷新或材料清理失败仅记录警告。
6. 等待任务成功，再检查关键业务数据和附件。保护备份可在历史或任务记录中下载。

账号恢复保留当前操作管理员的用户名、密码/完整钱包集合/邮箱登录凭据、用户名修改额度、管理员身份及当前会话。备份包含对应账号时恢复其业务资料和积分；缺少该账号时保留账号并将积分余额重置为 0。其他账号恢复备份状态，备份中不存在的账号移除，其旧会话和 MCP Key 撤销。与保留管理员任一钱包或其他登录凭据发生唯一性冲突时预检拒绝；MySQL 还会按实际字段排序规则检查备份内部的用户名、邮箱和钱包重复。数据库恢复始终覆盖，所有业务写入仍在同一个事务中；分页或逐条处理不产生部分提交。

业务恢复不替换目标环境的数据库连接、安装绑定、主密钥和备份控制状态。迁移到另一台主机或另一种数据库时，先独立安装目标环境、创建用于恢复的管理员，再上传完整包。主密钥及安装配置仍由部署管理，并单独备份。

## 中断与维护状态

切换附件前，应用将恢复意图和原/新根目录名称写入持久化日志，并同步文件和目录。数据库事务内写入专用提交标记；该标记不进入导出数据。

重启时，应用先检查恢复日志：存在提交标记则保留新数据并完成清理，否则撤销未提交的文件切换。恢复决定在删除材料前持久化，清理可重复执行。提交状态、日志或文件状态无法确认时，系统进入维护状态，保留日志、暂存和回滚目录，停止业务写入。不要删除 `config/backup-state/restore.json` 或上传目录下的 `.complete-restore-*`、`.complete-rollback-*` 来绕过维护；先恢复原数据库可达性和磁盘权限，再重启让应用协调。

备份目录本身不可用会在后台显示存储错误，不会自动改用业务目录。维护及任务错误使用脱敏代码；排查文件系统权限、磁盘剩余空间和数据库连接时不要把连接串、Cookie、Token 或密码放入日志。

## HTTP 接口

全部接口使用管理员 Session，位于 `/api/admin/mm/backup`。控制请求的 JSON 限制为 4 KiB；分片使用 `application/octet-stream` 请求体。

| 方法与路径 | 请求或结果 |
| --- | --- |
| `GET/PUT settings` | 读取状态；保存 `enabled`、`dailyTime`、`timeZone`、`retentionCount`。 |
| `GET snapshots` | 完整备份摘要、最近 100 个任务和当前任务。 |
| `POST snapshots` | 创建手动备份；可传失败/中断任务的 `retryJobId`。返回 202 和任务。 |
| `POST snapshots/import` | 传 `{ "importId": "UUID" }`，验证上传所有权并排队校验、发布持久备份；重复请求复用已有任务，返回 202。 |
| `GET/HEAD snapshots/[id]/download` | 使用备份 UUID 下载 ZIP，支持 Range、If-Range、ETag。 |
| `DELETE snapshots/[id]` | 传 `{ "confirm": "DELETE_BACKUP" }`，拒绝删除使用中的包。 |
| `POST imports` | 传 `size`、`fileName`、`lastModified`、`fingerprint`，返回 201 和管理员绑定的会话。 |
| `GET imports/[id]` | 查询总大小、分片大小、已确认偏移量、状态与过期时间；已提交导入时含 `importJobId`，发布后含 `snapshotId`。 |
| `PATCH imports/[id]` | 二进制分片；请求头 `Upload-Offset`、`X-Chunk-SHA256`，返回已确认偏移量；冲突返回 409 及服务端偏移量。 |
| `POST imports/[id]/complete` | 全部字节已确认后原子完成，返回 `importId`。 |
| `DELETE imports/[id]` | 取消并清理未被引用的会话。 |
| `POST restores/preview` | 传 `{ "snapshotId": "UUID" }` 或 `{ "importId": "UUID" }`，返回 202 和预检任务，任务完成后含预检摘要。 |
| `POST restores` | 传 `{ "previewId": "UUID", "confirm": "RESTORE_BACKUP" }`，返回 202 和恢复任务。 |
| `GET jobs/[id]` | 查询任务状态、阶段、进度及完成的预检摘要，不持有全局维护锁。 |

本地备份仍应另行复制到另一块磁盘或外部介质；与业务数据放在同一块盘的备份不能覆盖磁盘损坏。完整包包含密码哈希和个人数据，按敏感文件管理。SHA-256 用于完整性检测，不构成备份来源的数字签名；只恢复可信来源的包。

## 开发验证

默认的完整备份测试使用临时 SQLite 数据库和上传目录：

```bash
npm test -- src/server/services/admin-backup/complete.integration.test.ts src/server/services/admin-backup/uploads.test.ts src/server/services/admin-backup/large-backup.test.ts
```

大条目边界测试在本轮 Node 24.19.0 下写入并读取 65,536 个空文件条目，多次运行的进程 RSS 增量约 600–670 MiB，包含 ZIP 写入、目录解析及测试进程开销。这是该夹具的实测值，不是固定内存预算；大量条目仍需按运行环境评估内存。

同一套测试也支持 `SLOTHVAULT_BACKUP_TEST_PROVIDER=mysql` 或 `postgresql`，并通过 `SLOTHVAULT_BACKUP_TEST_CONTAINER` 指定专门创建的 Docker 容器完整 ID。测试只接受带 `slothvault.test=backup` 标签、数据库端口绑定到 `127.0.0.1` 的容器，在容器中逐项创建和删除独立测试库，不读取安装中的数据库配置。不要将这些变量指向业务容器。MySQL 容器使用测试专用的无密码 root；PostgreSQL 容器使用测试专用的 trust 认证。

当前 MySQL 历史迁移 `20260820000000_note_content_evidence` 会删除仍被外键使用的 `uq_release_credential_version_network` 索引，原样初始化隔离库会报 `ERROR 1553`。备份测试仅在临时库中提前补充等价普通索引，以验证备份服务；这不表示原有 MySQL 安装迁移已通过，也不修改已部署的迁移历史。
